## 1. 결론

| 구분 | 내용 |
|---|---|
| 현재 기본값 | **Claude Sonnet 5.5** (`claude-sonnet-5-5`) - 팀 저장소의 `.env.example`과 `packages/ai/src/client.js`에 설정된 값 |
| 비교 후보 | Claude Opus 5.5 (`claude-opus-5-5`, 더 비쌈), Claude Haiku 5.5 (`claude-haiku-5-5`, 더 쌈) |
| 확정 방법 | `npm run eval`(R-26 정확도 측정, 7장)에서 같은 케이스로 세 모델을 비교해 정한다 |
| 바꾸는 방법 | 코드는 그대로 두고 `.env`의 `AI_MODEL` 값만 바꾼다 |

핵심 기능(FR-007~009: 영수증 줄 단위 읽기 + 말로 나누기 + 규칙 검증 후 재시도)은 이미지 읽기와 판단을 함께 해야 해서 정확도가 가장 중요하다. 정확도가 Sonnet 5.5로 부족하면 Opus 5.5로 올리고, 충분하면 Haiku 5.5로 내려도 되는지 확인한다.

## 4. 선정 기준

1. **정확도**: R-26 지표(줄 금액 일치율, 배정 정답률, 오류를 잡아낸 비율)
2. **형식 고정**: 구조화 출력으로 항상 같은 모양의 결과를 받는지
3. **응답 속도**: 시연 중 영수증 한 장을 처리하는 시간
4. **비용**: 해커톤 크레딧은 잔액을 일반 API 키로 조회할 수 없어 총량을 모른다. 측정에서 요청 1건당 토큰 수(`usage`)를 기록해 비교한다.

## 5. 모델별 API 주의 사항

코드를 짤 때 아래를 지키지 않으면 400 오류가 난다.

| 항목 | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 |
|---|---|---|---|
| `thinking: {type: "disabled"}` | 400 오류 | 400 오류 (`between_tools` 사용) | 사용 가능 |
| `budget_tokens` | 400 오류 | 400 오류 | 400 오류 |
| `tool_choice`를 `any`/`tool`로 강제 | 400 오류 | 400 오류 | - |
| 마지막 assistant 메시지 미리 채우기(prefill) | 400 오류 | 400 오류 | 400 오류 |

공통으로 지킬 것:
- 결과 형식은 `output_config.format`(구조화 출력)으로 고정한다. 옛 `output_format` 파라미터는 쓰지 않는다.
- 응답을 쓰기 전에 `stop_reason`을 확인한다. `"refusal"`이면 AI가 처리를 거절한 것이므로, 직접 입력 화면(FR-017)으로 넘긴다.
- 생각의 깊이는 `output_config: { effort: "low" | "medium" | "high" }`로 조절한다. Opus 5.5는 기본값이 medium이라 원하는 값을 명시한다.

## 6. 적용 방법

팀 저장소(`hanatour-290-app`)에는 이미 모델을 환경변수로 바꾸는 구조가 있다. 측정 결과에 따라 `.env`의 `AI_MODEL`만 바꾸면 된다.

```
# 저장소 루트의 .env (cp .env.example .env) - 절대 커밋 금지
ANTHROPIC_API_KEY=...
AI_MODEL=claude-sonnet-5-5
```

`packages/ai/src/client.js`의 현재 코드:

```js
export const MODEL = process.env.AI_MODEL ?? 'claude-sonnet-5-5'
```

AI 호출 예시 (`packages/ai`에서 구조화 출력으로 결과 형식을 고정):

```js
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod'
import { getClient, MODEL } from './client.js'

const r = await getClient().messages.parse({
  model: MODEL,
  max_tokens: 4000,
  messages: [{ role: "user", content }],      // 영수증 이미지 + 말
  output_config: { format: zodOutputFormat(ReceiptSchema), effort: "medium" },
});
if (r.stop_reason === "refusal" || !r.parsed_output) {
  // 직접 입력 화면(FR-017)으로
}
```

## 8. 임베딩 모델 (기록 ↔ 예정 항목 연결)

카드 문자 · 말 · 영수증으로 남긴 기록이 일정의 예정 항목(선택관광 · 경비)과 같은 지출인지 후보를 찾는다 (노션 「AI 활용 방향」 추천 2). Claude 가 아니라 서버 안에서 돌리는 사전학습 문장 임베딩 모델이다. 추가 학습은 하지 않았다.

| 항목 | 내용 |
|---|---|
| 모델 | `Xenova/multilingual-e5-small` (ONNX, 8비트 양자화, 다국어, 384차원) |
| 실행 | `@huggingface/transformers` (Node, onnxruntime-node). API 비용 없음 |
| 흐름 | ① 상품 분석 때 Claude 가 예정 항목마다 다른 이름(`aliases`)도 만든다 (추가 호출 없음) ② 기록은 Claude 가 한국어 이름으로 읽는다("GOREME BALLOONS" → "괴레메 열기구 투어") ③ 양쪽에서 "투어" 같은 흔한 말을 빼고 임베딩 유사도(이름 · 별칭 중 최고) ④ 통화 · 금액 규칙 ⑤ 후보 1개 → 사용자가 "맞아요" |
| 코드 | `packages/ai/src/embed.js`(모델), `packages/ai/src/planMatch.js`(유사도), `packages/shared/src/match.js`(규칙), `POST /api/match/plan` |
| 규칙 값 | 점수 0.87 이상 · 금액 일치 +0.02 · 2등과 0.01 이상 차이 · 이름 유사도 0.86 이상 (금액만 같은 다른 가게는 잇지 않음) |
| 속도 | 로컬 모델 로드 약 2초 · 기록 1건 약 150ms(별칭 포함). Vercel 첫 호출 6.9초, 이후 0.4초 (2026-11-04 Preview, 별칭 넣기 전 측정) |

### 측정 방법

`npm run eval:match` (`packages/ai/eval/match/`), 교차검증은 `npm run eval:match -- --cv`. 데이터는 모두 **직접 만든 예시**이고 실제 상품 · 사용자 데이터가 아니다.

| 세트 | 상품 | 개수 (연결 없음) |
|---|---|---|
| 개발 `cases.json` | 튀르키예 (시연 상품) | 22 (8) |
| 확인 `holdout.json` | 튀르키예 | 20 (7) |
| 시험 `test/*.json` | 다낭 · 이탈리아·스위스 · 홋카이도 · 몽골 (가상 상품 문구) | 63 (21) |
| 합계 | 상품 5개, 통화 6종 (USD · EUR · CHF · JPY · TRY · KRW) | **105 (36)** |

- 예정 항목 · 별칭은 상품 문구를 실제 `estimate()` 로, 기록 이름은 실제 `readRecord()` 로 Claude(`claude-opus-5-5`)가 만든 것을 저장해 쓴다 (`prepare.js`, `aliases.js`, `names.js`). 앱과 같은 흐름이다
- "연결 없음" 케이스는 일부러 **같은 금액 · 같은 지명**으로 만들었다 (예: 오타루 편의점 1,800엔 ↔ 운하 크루즈 1,800엔)

### 지나온 값과 바로잡음

| 시점 | 규칙 값 | 처음 보는 데이터에서 |
|---|---|---|
| 1차 (임베딩 + 금액) | 0.80 / +0.02 / 차이 0.02 | 튀르키예 확인 60%, 잘못 연결 5건. 처음엔 개발 세트 숫자(82%, 0%)만 적었는데 그 세트에 맞춰진 값이었다 |
| 2차 (+ 흔한 말 빼기 + 별칭) | 0.87 / +0.06 / 차이 0.01 | 튀르키예 확인 80% · 2건이었지만, 새 상품 4개에서 잘못 연결 9건(14%). 금액 가산점이 커서 같은 금액의 다른 가게를 이었다 |
| **지금 (+ 이름 유사도 바닥)** | 0.87 / +0.02 / 차이 0.01 / 바닥 0.86 | 교차검증 83%, 잘못 연결 3% |

- 2등과 차이 0 은 후보에서 뺐다. 값이 아니라 "애매하면 묻지 않는다"(R-25) 원칙으로 정했다
- 남은 오류는 대부분 "못 찾음"(사용자가 일정에서 직접 "했다" 를 누르면 됨). 잘못 연결은 같은 지명 · 같은 금액(오타루 JR 열차표 → 운하 크루즈 등)
- 데이터가 105개라 1건이 약 1%p. 모두 직접 만든 예시라 실제 기록과 분포가 다를 수 있다

### 더 올리려면

- 실제 여행 기록이 쌓이면 그걸로 다시 잰다 (지금은 직접 만든 예시 105개)
- 같은 금액 · 같은 지명 항목(유람선 · 카트 · 아쿠아리움)은 이름만으로 가르기 어렵다 → 이런 애매한 경우만 Claude 에게 후보 2~3개 중 고르게 하는 방법(재순위)을 검토할 수 있다. 다만 호출이 하나 늘어난다
